# مراجعة جاهزية نانزا للمنافسة مع أنظمة ERP

التاريخ: 17 تشرين الأول 2026. هذه مراجعة معمارية موجّهة للكود الموجود، وليست شهادة تدقيق مالي أو اختبار اختراق أو إثبات تكافؤ مع منتج آخر. التعديلات محلية ولم تُنشر كإصدار جديد.

## القرار التنفيذي

الهدف المناسب أولاً: برنامج محاسبة وإدارة أعمال قوي للمؤسسات اللبنانية الصغيرة والمتوسطة، يعمل محلياً، ويدعم العربية وUSD/LBP والرواتب والضرائب مع رقابة واضحة. المنافسة لا تتحقق بعدد الأزرار أو بإضافة كلمة AI. معيار النجاح هو صحة القيد، اكتمال دورة المستند، سهولة المراجعة، وثبات التشغيل والاسترجاع.

لا أوصي بإعادة كتابة البرنامج كله الآن أو باستبدال SQLite لمجرد المقارنة مع ERP. أوصي بتثبيت عقد البيانات والاختبارات، ثم قياس الأداء قبل اختيار ترحيل قاعدة البيانات.

## القارئ: ما تغيّر الآن

- Prompt خاص ومختصر يطلب النسخ فقط، ويفصل subtotal عن grand total، ويمنع اختراع صفر للضريبة أو استنتاج سنة أو عملة.
- حقول معلّمة بالشك تبقى فارغة في الاقتراح حتى لو اتفق القارئان على نفس الرقم.
- التاريخ الرقمي القابل لتفسيرين يحتاج تأكيداً؛ لا نعتمد تقدير الموديل وحده لتمييز الغموض.
- الاحتفاظ بأسطر مكتوبة كما قرأها كل قارئ، وفحص كمية × سعر ومجموع الأسطر بصورة مستقلة، من دون إصلاح الأرقام لتوازن الحساب.
- الأسطر غير المؤكدة لا تتحول تلقائياً إلى أصناف أو قيود. شاشة المراجعة تعرض الفروقات والنص المقروء لكل قارئ.
- لا تغيير في ترخيص النماذج أو تشغيل خدمة مدفوعة. القارئ المحلي يبقى اختيارياً.

هذا تحسين للضوابط وعقد القراءة؛ ليس نتيجة اختبار دقة على الفواتير الحقيقية. النماذج الاختيارية غير مثبّتة ومفعّلة في بيئة هذه المراجعة، لذلك لم أشغّل استدلالاً حقيقياً بالـprompt الجديد. وتجارب الصور السابقة تضمنت أخطاء في المبالغ. هدف 80% لم يتحقق ولم يثبت.

## مراحل التنفيذ المقترحة

### P0 — الثقة قبل النشر

1. إغلاق فروقات الأرقام، ومعاملات الحفظ والموافقة والعكس، ومنع إعادة تنفيذ الطلب المالي نفسه عند إعادة المحاولة.
2. فحص ترقيات القاعدة من نسخ قديمة. أضفت migration دفعات الرواتب إلى بصمة المخطط، حتى يُكتشف تغيّرها لاحقاً.
3. اختبار Windows على جهاز مماثل لجهاز المستخدم؛ اختبار نسخة احتياطية واستعادة على جهاز آخر.
4. مجموعة فواتير مؤكدة: فصل صور التطوير عن صور التقييم، وقياس التاريخ والمورد والعملة والضريبة والمجموع والأسطر كلّاً على حدة. الفراغ لا يُحسب قراءة صحيحة لحقل موجود، والقيمة المخترعة في خانة فارغة تُسجّل خطأ.

### P1 — دورة أعمال مكتملة

- أمر شراء ثم استلام جزئي ثم فاتورة ثم دفعة، مع مراجعة فروقات الكمية والسعر.
- عرض/أمر بيع ثم تسليم وفاتورة وقبض ومرتجع، مع تتبع المصدر.
- لوحة استثناءات: مستند غير مرحّل، مطابقة غير مكتملة، رصيد غير مفسر، رقم متكرر، أو قراءة غير مؤكدة.
- قوالب الموردين تتعلم مواقع الخانات من تصحيح مؤكّد؛ لا تعيد استخدام تاريخ أو مبلغ فاتورة قديمة.

### P2 — توسع مبني على قياس

- API مُرقّم الإصدارات وتكاملات وبوابة رفع ومراجعة.
- قياس قاعدة بيانات كبيرة ومستخدمين متزامنين. ندرس PostgreSQL عند ظهور حاجة مُثبتة، مع خطة نقل ومطابقة الأرصدة.
- موافقات متعددة المراحل وصلاحيات حسب الدور والمستند، وفق الحاجة الفعلية.

## بوابات القبول

- القيد المتوازن وحده لا يثبت صحة الحساب أو الضريبة؛ نحتاج مطابقة مصدر-قيد-تقرير.
- كل عملية مالية لها اختبارات نجاح وفشل وتراجع، واسترجاع بعد توقف التنفيذ.
- لا نشر لقراءة تلقائية غير مراجعة قبل قياس أخطائها النقدية على فواتير مستقلة. هدف 80% قراءة لا يعني أهلية ترحيل آلي.
- مؤشرات الأداء وأحجام البيانات وعدد المستخدمين تُقاس ويُحتفظ بنتائجها؛ لا يوجد هنا ادعاء بتحمل حمل ERP كبير.
- لا نسمّي البرنامج مطابقاً لكل القوانين أو بديلاً مكافئاً لكل وحدات Odoo/Zoho قبل اختبارات قبول محددة.

## المقارنة الخارجية ومصادرها

المصادر الرسمية تؤكد أن المنافسة تشمل دورة الأعمال والتكاملات، وليس OCR فقط. توثيق Odoo يشرح مطابقة الفاتورة المرقمنة بأمر شراء. وصف Zoho Books يشمل أوامر البيع والشراء، الموافقات، بوابات العملاء والموردين، والتكاملات. هذه أمثلة وظيفية، وليست إثباتاً لدعم لبنان أو تساوي كل الإصدارات والخطط والأسعار.

- Odoo: https://www.odoo.com/documentation/18.0/applications/finance/accounting/vendor_bills/invoice_digitization.html — استُخدم ملخص المصدر الرسمي المفهرس؛ تعذّر فتح الصفحة كاملة في هذه المراجعة.
- Zoho Books: https://www.zoho.com/us/books/accounting-software-features/ — صفحة الوظائف الرسمية، تمت مراجعتها في 17 تشرين الأول 2026.
